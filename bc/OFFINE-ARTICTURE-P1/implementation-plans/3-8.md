# Phase 3.8: All Writes Go Through Sync Queue (No Direct Supabase)

**Goal:** No app code writes directly to Supabase. All writes: local first → add to sync queue → SyncWorker pushes to Supabase when online. Single path for data flow.

**Prerequisites:** Phase 1.1, 1.2, 1.3, 2.4–2.6, 3.7 (sync queue extended for streak, user_profile, user_settings).

## 2. Target Flow

```
User action (save entry, change settings, etc.)
    ↓
Write to local SQLite (is_synced=0)
    ↓
Add to sync_queue (or entries.is_synced=0 for entries)
    ↓
Trigger processSyncQueue (or let periodic/background handle)
    ↓
SyncWorker: if online → push to Supabase via SupabaseSyncService
    ↓
On success: mark local is_synced=1, remove from queue
```

**Rule:** SupabaseSyncService is only called by SyncWorker. No other code calls it for writes.

### Step 3.1: EntryProvider — Remove batchSaveEntry

**File:** `lib/providers/entry_provider.dart`

**3.1.1** In `_scheduleBatchSave` (or equivalent save flow):
- Keep: `_savePendingChangesToLocal` (writes to local, adds to sync_queue via LocalEntryService).
- Remove: `syncService.batchSaveEntry(...)`.

- Update: `ref.read(syncStatusProvider.notifier).setSaved()` — show "Saved locally" immediately; "Synced" when queue processed.

**3.1.2** Offline UX: User sees "Saved" right away. When online, sync happens in background. No blocking on Supabase.

## 5. Edge Cases

| Case | Handling |
|------|----------|
| First-time user, online | Create locally, add to queue. processSyncQueue runs, creates in Supabase. |
| First-time user, offline | Create locally, add to queue. Sync when online. |
| Duplicate user on Supabase | Sync fails with duplicate key. Fetch from Supabase, update local, mark synced. |
| Entry save, offline | Local save, queue. User sees "Saved". Sync when online. |
| Settings change, offline | Local save, queue. Sync when online. |
